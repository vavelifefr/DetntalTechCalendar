# UX Flows — Current Application Behavior

This document records the behavior currently implemented in the application. If an older prompt or requirement conflicts with the running application, use the current implementation as the baseline and update the stale document or test. Do not change application behavior as part of a documentation reconciliation.

## 1. Start and navigation

1. Open or create the single local SQLite database and apply pending migrations.
2. An empty database is a valid first launch; the application does not fill it with demo data.
3. Open the Calendar as the home screen. The operating-system date is marked green. Open Orders due today or earlier mark their deadline red; closed Orders do not add red Calendar marks.
4. The Calendar shows all open Orders below the grid when no date is selected. There is no separate `Ближайший заказ` action.
5. The main menu contains `Архив`, `Статистика`, `Долги`, `Прайс-лист`, `Настройки`, and `О программе`. Other screens show `Домой` beside the menu control.

## 2. Select a date and create an Order

1. Selecting a Calendar date filters the list to open Orders whose deadline is exactly that date. Selecting the same date again clears the selection.
2. Hide the New Order button when no date is selected. With a date selected, show `Новый заказ к : <date>` directly below the month grid.
3. Activating it opens the New Order card and pre-fills `Срок сдачи` with the selected date; that field remains editable. `Старт заказа` defaults to today and remains editable.
4. The selected-date list is titled `Активные заказы (<date>)`. If no open Order is due that day, hide the whole list and its totals.
5. The New Order card contains the patient label, Doctor, start date, deadline, optional Order comment, WorkItems, expenses, and a read-only financial summary. Patient, Doctor, and deadline are required by default and can be configured in Settings.

## 3. Add WorkItems and expenses to an Order

1. A new Order starts with `Работы (0)` and no expanded WorkItem editor. Choose `Добавить работу` to open one.
2. Choose a Work item from the `Работы` category in Pricing, or choose `Уникальная работа` and enter its name and accepted amount.
3. The selected Pricing metadata controls whether `Нумерация` and `Цвет` appear. FDI map and manual-number entry both save the same comma-separated permanent-tooth codes. A per-unit item without numbering shows `Количество`, starting at 1.
4. `Расчётная стоимость` is a temporary hint calculated from Pricing and quantity. It is not stored. The editable `Стоимость работы` is the accepted amount saved with the WorkItem; `(Изменено)` appears when it differs from the hint.
5. Saving a WorkItem collapses it into a card with its name and accepted amount. Cards are blue for `В работе`, green for `Выполнено`, and red for `Отменено`. Open a card to edit it. `Отмена` discards its unsaved edits and collapses it. `Удалить` asks for confirmation before removing that WorkItem.
6. `Работы (n)` also shows open, completed, and cancelled counts. Cancelled WorkItems stay visible as history but are excluded from work subtotals and provisional balances.
7. Expenses are entered below WorkItems using `Добавить к расходам`. Select an item from the `Расходы` category in Pricing, enter `Издержки`, `Количество` (default 1), and an optional comment. Save a red collapsed card showing the expense name and total. Each entry stores its name, unit price, quantity, total, and comment as a snapshot; the total is unit price multiplied by quantity.
8. The Order form requires at least one saved WorkItem. It validates required fields, FDI input, amounts, and dates. If the deadline precedes `Старт заказа`, the user can accept correction to a one-day Order ending on the start date or decline and continue editing.
9. Saving a new Order creates it and returns to the Calendar. Its ID is generated by the application and does not change.

## 4. Edit an existing Order and update production

1. Selecting an Order card from a Calendar list, Archive result, or another Order list opens that Order for editing. Its ID and lifecycle status are not editable.
2. WorkItems and expenses are initially collapsed. Open a card to edit its fields; save or cancel the editor before saving the whole Order or starting a financial action.
3. In an open Order, the two status buttons offer the statuses other than the current one. A status change is saved immediately and refreshes the counts and provisional summary. Completing the last WorkItem in `В работе` asks whether to open the normal Order closure form; declining keeps the Order open.
4. In a closed Order, WorkItem status and production dates remain editable, as do the Order details and WorkItems. The Order's lifecycle status and ID remain unchanged.
5. `Сохранить заказ` saves valid Order, WorkItem, and expense changes and stays on the card. `Сохранить и выйти` saves and returns to the Calendar.

## 5. Close an Order

1. Closing the Order is a separate explicit action. Before closure, every WorkItem still in `В работе` must be completed or deleted. Cancelled WorkItems are allowed and do not contribute to the expected amount.
2. The common closure form shows the expected amount (sum of completed WorkItem accepted amounts), `Получено`, expenses, the optional debt amount, and balance. `Получено` starts at the expected amount and can be edited.
3. The `Оформить как заказ с долгом` checkbox is disabled when received is equal to or above expected. If received is lower, the checkbox is available but starts unchecked. Leaving it unchecked closes without debt, so a discount or personal agreement is allowed. Checking it shows an editable debt amount, defaulted to expected minus received, and an optional debt comment.
4. The closure date may be in the past but cannot precede `Старт заказа`. If it does, the application offers to use the start date; declining returns to editing.
5. Confirming closure stores the receipt and, only when selected, a separate debt record. Realized income is the receipt plus later debt payments. Balance is realized income minus expenses. Unpaid debt is reported separately and does not reduce balance.

## 6. Record debt payments or forgive a remainder

1. A closed Order with debt exposes `Простить`, `Частями`, and `Погашен` actions. Each payment is stored separately and linked to that Order's debt.
2. A full payment defaults to the current remainder. A partial payment allows entry of an amount up to the remainder. A payment increases income and balance and reduces outstanding debt.
3. Forgiving the remainder requires confirmation. Saved payments remain in history and as income. The debt amount becomes the sum of saved payments, or zero when none were paid; the Order remains closed with debt history but no outstanding debt.
4. Before closure, repayment, or forgiveness, valid pending Order-card edits are saved in place. An open editor, validation error, or save failure blocks the financial action.

## 7. Archive and deletion

1. Archive results load after the user selects filters and presses `Поиск`.
2. Compact results show the patient, Doctor, and numeric closure date (`дд.мм.гггг`); they hide the Order ID. Selecting a result expands saved details and offers editing or confirmed deletion.
3. A red outline identifies an Order with outstanding debt. The expanded result retains historical saved values; it does not read current Pricing.
4. The bottom `Удалить все заказы` action requires typing `Удалить` and a second confirmation. It removes all Orders and linked WorkItems, expenses, debt, payments, and financial rows while preserving Pricing, directories, and Settings. Single-Order deletion removes the same linked data for that Order.
5. Existing or imported `CANCELLED` Orders remain visible in Archive. The web interface does not offer a new Order-cancellation action. A cancelled Order contributes zero income; its expenses remain included in Statistics when it has a closure date.

## 8. Statistics

1. Statistics filters closed Orders by their business closure date. Open Orders are not included.
2. Aggregates include closure receipts and debt payments as income, expenses, outstanding debt as a separate figure, and balance as income minus expenses. Unpaid debt does not reduce balance.
3. After editing saved data for a closed Order, aggregates remain at their previously calculated values until the user chooses `Обновить и пересчитать` for the selected period.
4. A Doctor card with outstanding debt has a red outline. Selecting the Doctor opens Archive with that Doctor preselected as a filter.

## 9. Pricing, Settings, and JSON exchange

1. Pricing has separate `Работы` and `Расходы` categories. Work entries provide temporary calculations for new WorkItems; expense entries provide default unit prices for new expense records.
2. Settings contains `Справочник врачей`, `Справочник Цветов`, required-field settings, Android reminder settings, and JSON import/export. Expenses are managed in Pricing, not as a Settings directory.
3. Doctor and Color directory exchange uses a directory JSON file. Pricing exchange includes both Work and Expense entries. A full-database JSON backup includes all local data.
4. Selective import replaces the selected dataset inside the active SQLite database and preserves unrelated data. Full restore replaces the database contents only after validation. JSON files are imports/exports, not separate live databases.

## 10. Android deadline reminders

1. Reminders are Android-only and opt-in. Defaults are disabled, 0 lead days, and 11:00 local time.
2. When enabled, an active Order can notify daily from 0–3 selected lead days before its deadline through the deadline day. Notification text includes patient, Doctor, and the deadline date.
3. Android notification and exact-alarm access are requested only when reminders are enabled. There is no boot receiver or `RECEIVE_BOOT_COMPLETED` permission; after a phone restart, reopening the application rebuilds the reminder schedule.
