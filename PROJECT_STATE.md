## Status

Within any horizontal row across the application, action buttons follow the left-to-right color order red, neutral white, blue, green. This changes placement only; colors, labels, and actions are unchanged. It applies to WorkItem status actions, debt actions, confirmation dialogs, and inline edit/delete controls. Before Order closure, full/partial debt repayment, or debt forgiveness, valid pending card edits are saved in place. An open work/expense editor or a validation/save error blocks the financial action; this save does not navigate to Calendar. The closure form has one `Закрыть заказ` entry action. Its `Оформить как заказ с долгом` checkbox is disabled when received is equal to or above expected; when enabled and checked, an editable debt amount is prefilled with expected minus received. Leaving it unchecked closes without debt even when received is below expected. In an existing Order, `Сохранить заказ` stays on the card; `Сохранить и выйти` returns to Calendar.

Archive now provides a bottom `Удалить все заказы` action with exact-text and final confirmations. It deletes Orders of every status and their linked financial/work data in one transaction while preserving Pricing, directories, and settings.

The expanded details of an Archive result also provide confirmed deletion of that single Order. Its card disappears from the current results after deletion, and linked work, expenses, debt, payments, and financial data are removed through the existing cascade. Order-card details show the current expected amount from completed WorkItems and current saved expenses after edits; realized income remains the closure receipt plus repayments. Main Statistics retains its stored aggregate values until the user explicitly recalculates. The active Order summary labels its calculated work total `Расчетная сумма`.

## Accepted high-level decisions

- Local-first application; web-first development, then validated Android APK packaging.
- SQLite is the primary persistent database. No SQL server or mandatory cloud service.
- Stack is recorded in `docs/design/adr/ADR-003-web-android-stack.md`.
- One Order has one immutable internal ID, one patient label, one Doctor relation, one editable acceptance date (`Старт заказа`), and one common deadline. The Order has no separate `created_at` date.
- If the deadline is earlier than `Старт заказа`, the user can accept correction to a one-day Order ending on its start date; declining returns to editing without saving.
- New Orders require a patient label, Doctor, and deadline by default; Settings can change these requirements. The acceptance date defaults to today and is editable, including for past dates.
- One Order contains one or more WorkItems. WorkItem name is required and quantity defaults to one. A new Order starts with zero saved WorkItems; at least one WorkItem must be saved to its draft before the Order can be created.
- Order is the Calendar record and the unit of accounting. A WorkItem is one type of fabrication or service inside an Order; the main menu and Calendar creation action are “Новый заказ”, and a child item is added with “Добавить работу”.
- An Order closes only through explicit user action. Open Orders appear in `Сводка по текущим заказам`; Archive also reads Orders with status `CANCELLED`. Main Statistics includes closed Orders and `CANCELLED` Orders with a business closure date. Cancelled Orders contribute zero income while their saved expenses remain included.
- Manual closure records a business closure date that cannot precede `Старт заказа`; Statistics groups closed Orders by this date, separate from the technical archive-transition timestamp.
- Each standard WorkItem shows a temporary calculated amount from Pricing and quantity to prefill its editable accepted amount. Pricing independently controls optional numbering and color fields; when numbering is hidden for a per-unit item, an editable quantity defaults to one. WorkItem header counts show open, completed/closed, and cancelled separately. Accepted WorkItem prices are kept as work history; expected amount at closure includes only completed WorkItems. Realized income is the closure receipt plus separate debt-payment entries. Expenses are multiple Order-level entries; the unpaid debt is a separate Order-linked record and does not reduce balance. Balance is income minus expenses.
- In the Order editor, standard work names come from Pricing. A unique WorkItem has a manual name and accepted amount, no Pricing position, and no quantity-based calculation; it contributes to the expected amount when completed, not directly to realized income.
- Order card, WorkItems, accepted amounts, expenses, and closed WorkItem status/production dates can be edited after closure. Current Pricing hints never replace saved accepted amounts. Statistics provides `Обновить и пересчитать` to refresh aggregates from saved values.
- Settings uses `Справочник врачей` and `Справочник Цветов`. The `directory` JSON file imports/exports these lists; expense positions are managed and exchanged as part of Pricing. Expense name, price, quantity, and total are saved as order-level snapshots.
- Permanent FDI codes are stored on each WorkItem as comma-separated text and parsed back for map display and unit count. The map and manual-number modes store the same codes. Migration 004 converts existing selections from the relation table; full-database JSON restore accepts schema versions 2–9.
- `Старт заказа` is the sole editable acceptance date. Migration 005 converts legacy `created_at` values to `order_date` and adds `closure_date`; it preserves technical `archived_at` separately.
- WorkItems may share start, completion, or cancellation dates. Calendar displays Order deadlines only.
- Archived financial values must not be recalculated from the current Pricing.
- Financial values are plain numbers; current screens and Pricing exchange files do not expose currencies. Legacy database columns remain for compatibility and do not affect calculations.
- The app uses one active local SQLite database. Versioned JSON selective imports replace the shared directory or Pricing; full restore replaces all database contents after validation.
- No Android emulator is needed for the current web preview. Web preview proportions follow POCO X7 Pro; the simulated device frame is never shown in the native Android application.
- S3 tooth selection uses FDI codes for permanent teeth only. Milk teeth are deferred to an optional post-release feature.
- The S3 odontogram uses the supplied FDI map artwork; circular FDI controls select teeth and highlight their matching illustrations. Artwork and button/tooth coordinates are separate from selection and persistence logic for later design updates.
